# Generate a Spec

Input: the approved `scenario.md`. Output: a `scenario.spec.ts` that proves each Expected item, a run result, and a report for the human.
`e2e` is the helper script command from `SKILL.md`. `<path>` is `<area>/<scenario>`.

The rules of `reference/contract.md` apply. Do not edit `scenario.md` in this procedure.

## 1. Read the scenario

1. Read `e2e-scenarios/<path>/scenario.md`.
2. Run `e2e hash <path>`. Keep the output for the spec header.
3. If the page does not show something that you need, read the source code. Examples: validation rules, test IDs, the routes of the feature. The source code does not replace sections 2 and 3. Do each scenario in the live application, also when the code looks sufficient.

## 2. Start a debug session

The session opens the application in the same state that a test starts in.

1. In the scripted auth mode, get a new session first:

   ```bash
   npx playwright test --config e2e-scenarios/playwright.config.ts --project=setup
   ```
2. Start the seed test **in the background**:

   ```bash
   npx playwright test e2e-scenarios/seed.spec.ts --config e2e-scenarios/playwright.config.ts --project=seed --no-deps --debug=cli
   ```
3. Read the output of that command until it shows `playwright-cli attach tw-<id>`.
4. Attach, then let the seed run:

   ```bash
   npx playwright cli attach tw-<id>
   npx playwright cli -s=tw-<id> step-over
   ```
   Read the output of each `step-over`. Run it again only while the output does not show `Close context`. When it shows `Close context`, the seed is complete and the page stays open. One more `step-over` ends the session.

   Add `-s=tw-<id>` to each command below.

If the debug session does not start, use this fallback: `npx playwright cli open <base URL>`, then `npx playwright cli state-load e2e-scenarios/.auth/state.json`, then `npx playwright cli goto <base URL>`.

## 3. Do each scenario in the application

Do one scenario at a time, in the live application. Each action prints `Ran Playwright code` with the exact code of that action. That code is the source of the spec. The live application also shows defects that the code does not show.

| Task | Command |
|------|---------|
| See the page | `snapshot`, or `find "<text>"` on a large page |
| Act | `click <ref>`, `fill <ref> "<text>"`, `select <ref> "<value>"`, `check <ref>`, `press <key>`, `upload <file>` |
| Get a locator for an assertion | `--raw generate-locator <ref>` |
| Read a value for an assertion | `--raw eval "el => el.textContent" <ref>` |
| Look for application errors | `console`, `requests` |
| All other commands | `npx playwright cli --help` |

Rules for this step:

- **Navigate through the UI.** Use links, menus, and buttons. Do not use `goto` for a page inside the application.
- **Check each page change.** After an action that changes the page, take a snapshot before the next action.
- **Record the direct path only.** Leave out the mistakes and the retries.
- **Use new data for each run.** If a scenario creates a record, make its name different each time, for example with `Date.now()`.
- **Look at each Expected item in the live page.** Get the locator and the value that prove it.
- **If the scenario says that the user is not authenticated,** run `cookie-clear` and `reload` before the scenario.
- **Write down each issue that you see:** a defect, a confusing flow, a slow page, a missing label. These become findings.

**If the application does not do what an Expected item says:** do not change the item, and do not select a weaker result. Write the assertion that the item states. Record a finding. The test will fail, and that is the correct result.

Tests are independent. After each scenario, run `resume` to end the session. Then start a new debug session for the next scenario.

## 4. Write the spec

Write `e2e-scenarios/<path>/scenario.spec.ts` in this form. Each part is required.

```typescript
// Generated by /e2e:run. The scenario file is the contract.
// scenario: e2e-scenarios/<path>/scenario.md
// scenario-sha256: <output of `e2e hash <path>`>
import { test, expect } from "@playwright/test";

// Test data. Change these values for your environment.
const NOTE_TEXT = `E2E note ${Date.now()}`;

test.describe("<title of scenario.md>", { annotation: [{ type: "covers", description: "<the Covers line>" }] }, () => {
  test("<scenario name, copied>", async ({ page }) => {
    // Enter the application. Go to the start location through the UI.
    await page.goto("/");
    await page.getByRole("link", { name: "Notes" }).click();

    // <What the next actions do, from the Description>
    await page.getByRole("textbox", { name: "New note" }).fill(NOTE_TEXT);
    await page.getByRole("button", { name: "Add note" }).click();

    await test.step("E1: <Expected item 1, copied>", async () => {
      await expect(page.getByRole("status")).toHaveText("Note added");
    });
    await test.step("E2: <Expected item 2, copied>", async () => {
      await expect(page.getByRole("list", { name: "Notes list" }).getByText(NOTE_TEXT)).toBeVisible();
    });
  });
});
```

- One `test` for each scenario. One `test.step` for each Expected item, with the title `E<n>: <text>`.
- Put each Expected step at the point in the flow where its result is visible.
- If the Expected text has double quotes, write the step title in single quotes. Do not change the text.
- Use the action code that the browser CLI printed.
- If the scenario has no `Covers:` line, omit the annotation argument.
- If the scenario context says that the user is not authenticated, add `test.use({ storageState: { cookies: [], origins: [] } });` above `test.describe`.
- If a scenario needs a file, create a small fixture in the scenario folder. Get its path with `path.join(path.dirname(test.info().file), "<name>")`.

Assertions:

| To prove | Use |
|----------|-----|
| A page or a redirect | `await expect(page).toHaveURL(/.../)` |
| Exact text | `toHaveText("...")` on a locator that does not use that text, for example a role, a label, or a test ID |
| An element is shown | `toBeVisible()` |
| A field value | `toHaveValue("...")` |
| A checkbox state | `toBeChecked()` |
| A number of rows | `toHaveCount(n)` |
| The structure of a region | `toMatchAriaSnapshot(...)` with only the necessary lines |

An assertion waits for its condition. Thus an Expected step needs no other wait.

### A scenario that types the real credentials

A trace records each typed value. Thus a login scenario needs these three steps:

1. In the spec, read the values from `process.env.E2E_USERNAME` and `process.env.E2E_PASSWORD`. The config loads `.env`.
2. Copy the login actions from `auth.setup.ts`. Do not type the credentials with the browser CLI.
3. Add `test.use({ trace: "off" });` above `test.describe`, so that the password is not written to a trace.

## 5. Check and review

1. Run `e2e check <path>`. Correct the spec until the output is `OK`.
2. Start the `e2e:spec-reviewer` subagent. Give it the paths of the scenario and the spec. Wait for its result before the next step.
3. Apply each item in its `Must fix` list.
4. For each item in its `Assertion concerns` list, make the assertion prove the full Expected text. If the application does not permit that, keep the strict assertion and record a finding.
5. Run `e2e check <path>` again.

## 6. Run

1. End the debug session with `resume`. Then run `npx playwright cli close-all`.
2. Run `e2e run <path>`.
3. If a test fails, read `triage.md` and follow it. After a first generation, the usual cause is a defect in the new actions. You can correct actions. Do a maximum of three rounds.

## 7. Report

Give the human these four parts, in this sequence:

1. **Results.** The output of `e2e run <path>`, without changes.
2. **Assertion map.** Copy the table that `e2e map <path>` prints. Do not rewrite a cell. Say: "This map shows how the test proves each Expected item. Review it."
3. **Findings.** Write them to `e2e-scenarios/<path>/findings.md` in the format below, and show them. If there are none, say "No findings".
4. **Decisions for the human.** Each Expected item that the application does not satisfy, and each question that stopped you.

Format of `findings.md`. One line for each finding. The human sets `[x]` when the finding is closed.

```markdown
# Findings: <path>

- [ ] <date> | <blocker, major, or minor> | <bug, ux, performance, or accessibility> | <location> | <what occurred> | <workaround, if you used one>
```

Append to the file if it exists. Do not remove lines.
